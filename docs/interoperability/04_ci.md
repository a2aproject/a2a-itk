# ITK in CI

ITK runs in two places:

- **In each SDK repository**, against that SDK's working tree. This is where interoperability is actually gated: a pull request job and a nightly job.
- **In this repository**, to test ITK itself (unit tests, image build) and to publish the dashboard.

## In an SDK repository

Every SDK repo has the same three pieces:

| Piece | Where | What it does |
| --- | --- | --- |
| `itk/run_itk.sh` | SDK repo | A ten-line shim: sets `ITK_SDK_NAME`, defines proto codegen for its language, clones `a2a-itk`, and sources the shared driver |
| `scripts/run_itk_shared.sh` | this repo | The driver. Builds and starts the ITK container, mounts the SDK into it, posts the scenarios, reports the result |
| two workflows | SDK repo | `itk.yaml` (pull requests) and a nightly one, both of which just run `run_itk.sh` with different environment variables |

The driver is shared so the five-then-six per-SDK scripts could stop drifting: before it existed, three of them printed PASSED for every scenario regardless of outcome. The configuration table, hook functions and a copy-pasteable shim for each language are in [`scripts/README.md`](../../scripts/README.md); this page describes the flow.

### What the driver does

1. **Proto.** Copies `protos/instruction.proto` into the `itk/` directory (unless `ITK_COPY_PROTO=0`; Java and Rust read it from the checkout) and runs the shim's `itk_generate_protos` hook. The SUT's stubs are generated on the host, before the container exists - the launcher generates stubs for fetched peers but not for the mounted SUT.
2. **Image.** `docker build -t itk_service <a2a-itk>`, unless `ITK_SKIP_BUILD=1`. CI sets it and builds with `docker/build-push-action` instead, to get GitHub Actions layer caching. Podman is detected and used if Docker is absent.
3. **Container.** Starts `itk-service` on port 8000 with:
   - the SDK repo mounted at `/app/agents/repo` and its `itk/` directory at `/app/agents/repo/itk` (the latter mount is skipped when `ITK_MOUNT_ITK_DIR=0`);
   - `~/.cache/a2a-itk-launcher` on the host mounted at `/root/.cache/a2a-itk` so peer builds survive between runs;
   - `itk/logs` mounted at `/app/logs` when `ITK_LOG_LEVEL=DEBUG`, which makes the service write one log per agent;
   - `ITK_READINESS_TIMEOUT=180` and `ITK_MAX_WORKERS=2` by default, both tuned for a small CI runner; `ITK_SCENARIO_TIMEOUT` is passed through only when the caller set it, otherwise the service's own 60 s default applies.

   It then marks the mounted trees as git `safe.directory` inside the container, because they are owned by a different user than root and git would otherwise refuse to read them.
4. **Readiness.** Polls `GET /health` for up to 60 seconds.
5. **Scenario file.** `SCENARIO_FILE` if set; otherwise with `ITK_SCENARIO_SET=shared` the shared `pr.yaml` or `nightly.yaml` from this repo, and with the default `local` the SDK's own `scenarios.json` or `scenarios_full.json`. `ITK_NIGHTLY_RUN=true` picks the nightly variant in both cases.
6. **Request body.** Runs `python -m test_suite.scenarios.build_request` **inside the container** to turn the file into a `/run` body. It runs there because YAML needs PyYAML, which the image has and a bare runner may not. `ITK_MATRIX_SDK` is passed as `sut_sdk` so `test_when` and `include_own_lines` resolve for the right SDK.
7. **Run.** `POST /run`, response saved as `raw_results.json`. The request runs under `curl --max-time $ITK_RUN_TIMEOUT` (1800 s by default), the backstop for everything the per-scenario deadline does not cover, cold peer builds included. If it trips, the step fails with `Error: /run did not finish within 1800s (ITK_RUN_TIMEOUT)` and the service log is dumped.
8. **Report.** `scripts/itk_report.py` validates the response shape first (so a FastAPI error envelope can never be mistaken for results) and prints a per-scenario table. On a PR run it exits non-zero unless `all_passed`.
9. **Nightly only.** `scripts/process_results.py` downloads the SDK's rolling history, appends this run, and writes `itk_<sdk>.json` for the workflow to upload. On this path scenario failures are data, not a broken job - the step fails only if the service errored or the response was malformed.
10. **Cleanup** on exit: stop and remove the container, run the shim's `itk_extra_cleanup`, remove the copied proto and request files. The image is kept (`ITK_REMOVE_IMAGE=0`) and `raw_results.json` is left behind for the workflow.

If the run failed, the container log is printed before exit.

### The pull request workflow

Triggered on `push` to `main` and on `pull_request` touching the SDK source, `itk/`, the lockfile or the workflow itself. The steps every SDK's `itk.yaml` shares:

```yaml
- uses: actions/checkout@v7                     # the SDK
- uses: astral-sh/setup-uv@v7
- uses: actions/checkout@v7                     # a2a-itk, into itk/a2a-itk
  with: {repository: a2aproject/a2a-itk, ref: main, path: itk/a2a-itk}
- uses: docker/setup-buildx-action@v3
- uses: docker/build-push-action@v7             # itk_service:latest, GHA layer cache
  with: {context: itk/a2a-itk, tags: itk_service:latest, load: true,
         cache-from: type=gha,scope=itk_service, cache-to: type=gha,mode=max,scope=itk_service}
- uses: actions/cache@v6                        # peer checkouts and builds
  with: {path: ~/.cache/a2a-itk-launcher, key: itk-launcher-${{ runner.os }}-${{ github.sha }},
         restore-keys: itk-launcher-${{ runner.os }}-}
- run: bash run_itk.sh
  working-directory: itk
  env: {A2A_ITK_REVISION: main, ITK_SKIP_BUILD: "1"}
```

`A2A_ITK_REVISION` is which ref of this repo to use. CI pins `main`; a breaking change here therefore reaches every SDK's next PR run, which is the intended coupling - and the reason the `/run` request and response shapes, `/health` and port 8000 are frozen.

The job fails when any scenario fails. There is no `continue-on-error`: ITK is a merge gate.

### The nightly workflow

Same steps, on a cron at 02:00 UTC with `workflow_dispatch` for manual runs, plus:

```yaml
env: {A2A_ITK_REVISION: main, ITK_NIGHTLY_RUN: "True", ITK_SKIP_BUILD: "1"}

- uses: softprops/action-gh-release@v3
  with: {tag_name: nightly-metrics, prerelease: true, files: itk/itk_<sdk>.json}
```

The nightly set is the SUT against every peer in `matrix.yaml`, one pair per scenario, so it is both larger and slower than the PR set and may take over an hour with cold caches. The `nightly-metrics` release is a permanent, rolling pre-release in the SDK's own repository; its one asset per suite is overwritten every night.

### The published history

`itk_<sdk>.json` is a list of runs, newest last, capped at 50 (`ITK_HISTORY_LIMIT`):

```json
{
  "timestamp": "2026-10-06T02:14:09+00:00",
  "commit_sha": "...",
  "github_run_id": "...",
  "all_passed": false,
  "scenarios": [
    {"name": "Nightly - current vs go_v10 - send message - grpc - streaming",
     "passed": true, "sdks": ["current", "go_v10"], "edges": ["0->1", "1->0"],
     "protocols": ["grpc"], "behavior": "send_message", "streaming": true, "tier": "nightly"}
  ]
}
```

Each scenario record carries its own metadata, so the processor never has to look a result name up in a scenario file. It refuses to publish an empty run or a run where any result could not be recorded, because a partial entry would silently push a real one out of the window.

A total cluster failure (the SUT did not start) is published as a run with every scenario failed and the reason in the service response, rather than as a missing night. See `startup.cluster_error` in [01_running.md](01_running.md#post-run).

### Reading a failed CI run

In order of how often it is the cause:

1. **A scenario failed.** The `itk_report.py` table in the job log names it. The transport and peer are in the name. The container log, dumped right after, has the full request, the SSE events and which trace tokens were missing.
2. **A peer failed to build or start.** Look for `peer(s) failed to start and were dropped` in the log. The run continued without that peer; the warning lists which scenarios were trimmed or skipped. The peer's own output is only captured with `ITK_LOG_LEVEL=DEBUG`, so re-run the workflow with that if the cause is not obvious.
3. **The SUT failed to start.** `the code under test ('current') failed to start`. Usually missing proto stubs (the `itk_generate_protos` hook) or a build error in the SDK itself.
4. **`git ls-remote` timed out** -> HTTP 502 from `/run`, reported by `itk_report.py` as a service error. Re-run the job.
5. **Nothing runnable.** HTTP 400 with "resolved to nothing runnable". Every scenario was filtered by `test_when` or excluded as a known failure for this `sut_sdk`. Check `known_failures.yaml` and the shared set.
6. **A scenario hit its deadline.** `INTEGRATION TEST FAILED: <name> did not finish within 60s (ITK_SCENARIO_TIMEOUT)` in the container log. One hop never answered and never closed its stream; the scenario is failed and the rest of the run is unaffected. The name says which pair and transport.
7. **The whole run hit its deadline.** `Error: /run did not finish within 1800s (ITK_RUN_TIMEOUT)` from the driver. Usually many slow peer builds on a cold cache, or a service that stopped making progress; the service log is printed right after.

## In this repository

[`.github/workflows/ci.yml`](../../.github/workflows/ci.yml), on every push to `main` and every pull request:

- builds the container image (with layer caching, no push), so a Dockerfile change that breaks the build is caught here rather than in six SDK repos;
- runs `ruff check` and `uv run pytest`. The unit tests cover the launcher, the resolver, exclusions, the traversal engine, the service handlers and the result scripts, all without network.

There is no end-to-end run of real agents in this repo's CI. That happens in the SDK repos, which is also where a change to a shared scenario set shows its effect.

### The dashboard

[`.github/workflows/deploy_dashboard.yml`](../../.github/workflows/deploy_dashboard.yml) runs daily at 04:00 UTC - two hours after the SDK nightlies - on manual dispatch, and on pushes that touch `dashboard/`:

1. `dashboard/scripts/fetch-metrics.sh` downloads `itk_<sdk>.json` and `acts_<sdk>.json` from each SDK's `nightly-metrics` release into `dashboard/public/`. An SDK that has not published yet gets an empty list, not an error.
2. `npm test` typechecks and tests, `npm run build` produces the static site.
3. The result is deployed to GitHub Pages under `/dashboard/`: <https://a2aproject.github.io/a2a-itk/dashboard>.

The dashboard is a daily snapshot, not live monitoring. It shows the latest night per SDK and the trend over the rolling window.

To add an SDK to it: make its nightly publish `itk_<sdk>.json` to a `nightly-metrics` release, add a `fetch` line to `fetch-metrics.sh`, and add the SDK to `dashboard/src/shared/sdks.ts`.
