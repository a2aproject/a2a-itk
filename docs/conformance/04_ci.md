# ACTS in CI

ACTS runs in the same two places as ITK, through the same machinery:

- **In each SDK repository**, on pull requests and nightly. The jobs reuse the SDK's `itk/run_itk.sh` shim and this repo's shared driver; one environment variable switches the driver from the traversal suite to the conformance corpus.
- **In this repository**, only the runner's unit tests. No real SDK is tested here.

Everything about containers, mounts, caches and the shim is identical to the traversal path and is described once, in [interoperability/04_ci.md](../interoperability/04_ci.md). This page covers what is different.

## In an SDK repository

### The switch

`ITK_ACTS_RUN=1` makes the driver run ACTS instead of a traversal. It is a separate switch from `ITK_NIGHTLY_RUN`, which decides whether results are gated or recorded, so the four combinations all mean something:

| | `ITK_NIGHTLY_RUN` unset | `ITK_NIGHTLY_RUN=true` |
| --- | --- | --- |
| `ITK_ACTS_RUN=0` (default) | traversal, job fails unless `all_passed` | traversal, append to `itk_<sdk>.json` |
| `ITK_ACTS_RUN=1` | ACTS, job fails unless conformant on every binding | ACTS, append to `acts_<sdk>.json` |

The ACTS-specific configuration, all read by `scripts/run_itk_shared.sh`:

| Variable | Default | Meaning |
| --- | --- | --- |
| `ITK_ACTS_RUN` | `0` | `1` or `true` selects the ACTS path |
| `ITK_ACTS_TRANSPORTS` | `jsonrpc` | Comma-separated bindings, one `POST /run-acts` each. CI sets `jsonrpc,grpc,rest` (`jsonrpc,rest` for .NET, which has no gRPC server) |
| `ITK_ACTS_LANGUAGE` | `ITK_SDK_NAME` | Goes into the report's `sdk.language` |
| `ITK_SDK_REPO` | `a2a-<ITK_SDK_NAME>` | Goes into `sdk.name` and `sdk.repository`, and names the release asset URL |
| `ITK_METRICS_NAME` | `ITK_SDK_NAME` | The `<sdk>` in `acts_<sdk>.json` |
| `ACTS_HISTORY_LIMIT` | `7` | Runs kept in the rolling history (read by `process_acts_results.py`) |

### What the driver does on the ACTS path

Steps 1-5 of the traversal flow run unchanged: proto copy and codegen, image build (skipped in CI), container start with the SDK mounted at `/app/agents/repo`, `safe.directory` fixes, `/health` polling. The driver even picks a scenario file and builds a `/run` request body, which the ACTS path then ignores - a harmless leftover of the branch point being late in the script. Then, instead of `POST /run`:

1. **For each binding** in `ITK_ACTS_TRANSPORTS`, write `acts_request.json`:

   ```json
   {
     "transport": "jsonrpc",
     "sdk": "a2a-python",
     "language": "python",
     "repository": "https://github.com/a2aproject/a2a-python",
     "variables": {
       "insufficientAuthToken": "itk-insufficient-token",
       "otherUserTaskId": "00000000-0000-0000-0000-0000000000ff"
     }
   }
   ```

   The two variables are the ones the corpus references but never defines; `acts_runner` would supply the same values if they were left out, so they are here for visibility rather than effect.
2. `POST /run-acts`, response saved as `acts_results_<transport>.json`. Each request starts a fresh SUT inside the container; three bindings mean three agent starts, in sequence.
3. **Validate and summarise** with `scripts/acts_report.py`. It checks the payload is a real report (not a FastAPI error envelope, not empty) and prints the per-level tally, every failing test with its message, and every test that could not run because its precondition is unsatisfiable by any agent. On the PR path it runs with `--require-conformant`, which makes it exit non-zero unless the binding is conformant; on the nightly path a failure is a metric, not a broken job.

   ```
   --------------------------------------------------------
   ACTS CONFORMANCE (jsonrpc): a2a-go / jsonrpc
   --------------------------------------------------------
   101 tests in 43850ms
     MUST   56/59 passed (3 failed)
     SHOULD 24/29 passed (5 failed)
     MAY    12/13 passed (1 failed)

   9 failing test(s):
     CORE-SEND-004: expected an error, but the call succeeded
     STREAM-SUB-003: expected an error, but the stream opened and produced 1 event(s)
     ...
   --------------------------------------------------------
   CONFORMANCE: NOT CONFORMANT
   --------------------------------------------------------
   ```

   The script does no arithmetic of its own; every number is read out of the report's `summary`, so what it prints is what the dashboard sees.
4. **Keep the report** under its section 13.5 name, `acts-report-<sdk>-<transport>-<timestamp>Z.json`, next to the stable `acts_results_<transport>.json`. The workflow uploads the former as a build artifact; it is the file to open when a test failed.
5. **Nightly only.** After all bindings, `scripts/process_acts_results.py` takes every report, downloads the SDK's rolling `acts_<sdk>.json`, appends **one** entry covering all bindings, prunes to the limit and writes the file for the workflow to upload.
6. Exit with the first non-zero status collected along the way. On failure the container log is printed first.

A binding whose SUT would not start comes back as HTTP 400 from `/run-acts`; `acts_report.py` reports it as a service error and the step fails regardless of path, so a broken agent cannot be published as a clean night.

### The pull request workflow

Every SDK has an `acts.yaml` (`run-acts.yaml` in a2a-js) next to its `itk.yaml`. It is the same job with a different `env` block:

```yaml
on:
  push: {branches: [main]}
  pull_request:
    paths: ['src/**', 'itk/**', 'acts/**', 'pyproject.toml', 'uv.lock',
            '.github/workflows/acts.yaml']            # per language, of course

steps:
  # checkout, uv, clone a2a-itk, buildx, build itk_service with GHA cache,
  # restore ~/.cache/a2a-itk-launcher - identical to itk.yaml
  - name: Run ACTS Conformance Suite
    continue-on-error: true
    run: bash run_itk.sh
    working-directory: itk
    env:
      A2A_ITK_REVISION: main
      ITK_ACTS_RUN: "1"
      ITK_ACTS_TRANSPORTS: jsonrpc,grpc,rest
      ITK_SKIP_BUILD: "1"
  - uses: actions/upload-artifact@v7
    if: always()
    with: {name: acts-reports-<sdk>, path: itk/acts-report-*.json, retention-days: 14}
```

Two things to notice:

- `acts/**` is in the trigger paths. The behaviour contract `acts/sut-behaviors.yaml` changes what the runner demands of the agent, so editing it must re-run the suite.
- **`continue-on-error: true`.** The driver gates on `must` conformance, but the step is marked advisory, so a red ACTS job does not block a merge anywhere. The line was added when no SDK was conformant; the [dashboard](https://a2aproject.github.io/a2a-itk/dashboard/) shows which are now, and the workflow comment says what to do - delete that line to make ACTS a merge requirement. Until then the ITK job is the gate and the ACTS job is the report.

### The nightly workflow

`acts-nightly.yaml` (`run-acts-nightly.yaml` in a2a-js) is kept separate from the traversal nightly so neither shows red for the other's failure and each can be re-run alone. Compared with the PR job:

```yaml
on:
  schedule: [{cron: '0 2 * * *'}]        # a2a-java runs at 00:00 UTC
  workflow_dispatch:
permissions: {contents: write}           # to update the release

    env:
      A2A_ITK_REVISION: main
      ITK_ACTS_RUN: "1"
      ITK_ACTS_TRANSPORTS: jsonrpc,grpc,rest
      ITK_NIGHTLY_RUN: "True"
      ITK_SKIP_BUILD: "1"
  - uses: actions/upload-artifact@v7      # retention-days: 30
  - uses: softprops/action-gh-release@v3
    with: {tag_name: nightly-metrics, prerelease: true, files: itk/acts_<sdk>.json}
```

There is no `continue-on-error` and none is needed: with `ITK_NIGHTLY_RUN` set the driver does not gate on conformance. The step fails only if the service errored or a report came back malformed, which is exactly when nothing should be published.

Artifacts are kept 30 days, longer than the PR job's 14, so that every entry still inside the seven-run history window has its full report to look up.

### The published history

`acts_<sdk>.json` on the `nightly-metrics` release is a list of runs, newest last, capped at 7. One nightly over three bindings is **one entry**, with the bindings nested - one commit tested three ways is one run of the SDK, and three entries per night would shrink the window to two nights:

```json
{
  "timestamp": "2026-10-06T02:31:44+00:00",
  "commit_sha": "...",
  "github_run_id": "...",
  "sdk": "a2a-python",
  "sdk_version": "...",
  "acts_version": "1.0",
  "spec_version": "1.0",
  "transports": ["grpc", "jsonrpc", "rest"],
  "conformant": false,
  "summary": {"total": 281, "passed": 240, "failed": 9, "skipped": 32, "errors": 0, "duration_ms": 184021},
  "results": {
    "jsonrpc": {
      "conformant": false,
      "summary": {"total": 101, "passed": 88, "failed": 3, "skipped": 10, "errors": 0, "duration_ms": 61240},
      "by_level": {"must": {"total": 59, "passed": 52, "failed": 2, "skipped": 5, "errors": 0}, "should": {}, "may": {}},
      "tests": [
        {"id": "CORE-SEND-001", "level": "must", "result": "pass"},
        {"id": "CORE-HIST-003", "level": "must", "result": "fail",
         "failure": {"message": "...", "step_id": "get", "expected": "4", "actual": "3", "assertion_path": "history.length"}},
        {"id": "PUSH-CONFIG-001", "level": "must", "result": "skip", "skip_reason": "..."}
      ]
    },
    "grpc": {"...": "..."},
    "rest": {"...": "..."}
  }
}
```

The top-level `conformant` is the conjunction over bindings; `summary` is the sum, for a single trend line. Each test carries its id, level and result, plus the failure detail or skip reason when it did not pass - enough to tell "same failure as last night" from "new failure" without opening the artifact. Deliberately left out: the test name (static per id), duration (noise) and the per-step breakdown (the bulk of a report; it stays in the artifact). The window is 7 rather than ITK's 50 because an entry is an order of magnitude larger, and the asset is fetched by a browser on every dashboard load.

The processor refuses to publish a report with no tests, two reports claiming the same transport, or anything after a non-404 error fetching the existing history - each of those would overwrite a real window with a damaged one.

### Reading a failed run

1. **`CONFORMANCE: NOT CONFORMANT`** in the step log, with a list of failing tests. The message names the step, the assertion path and the expected and actual values. For the full request and response, download the `acts-reports-<sdk>` artifact and open the test's `steps`.
2. **`SUT does not declare behavior(s) tck-...`** on many tests at once: the SDK's `acts/sut-behaviors.yaml` is behind the corpus. Either implement the prefix or accept the failures; see [05_sdk-integration.md](05_sdk-integration.md#2-behaviors).
3. **`N test(s) COULD NOT RUN`** followed by `PRECONDITION CANNOT BE SATISFIED`: the corpus asks for a capability the protocol does not define. This never fails the job; it is a corpus problem to report upstream.
4. **`Invalid ACTS report: service returned an error: ...`**: `/run-acts` answered 400 or 500. The usual reason is the SUT not starting - a missing proto stub, a build error, or a readiness timeout. The container log is printed right after; with `ITK_LOG_LEVEL=DEBUG` the agent's own output is in `itk/logs/`.
5. **Skips you did not expect** (`agent card capability X=False`): the card does not advertise `X`. If the SDK does implement it, the test agent forgot to say so.

## In this repository

[`.github/workflows/ci.yml`](../../.github/workflows/ci.yml) runs the unit tests under `tests/test_acts_*.py`: the loader against the real mirrored corpus, the schema, variables and assertions, all three dispatchers against canned responses, the gating and deviation logic, the report builder and the two CI scripts. None of it needs an SDK or the network. A change to the runner is checked here; its effect on a real SDK only shows in that SDK's next ACTS run.

### The dashboard

The same `deploy_dashboard.yml` that builds the ITK pages also fetches `acts_<sdk>.json` from each SDK's `nightly-metrics` release (`dashboard/scripts/fetch-metrics.sh`) and renders it from `dashboard/src/acts/`: per SDK, the latest night's verdict per binding and the trend over the window. Like the ITK view it is a daily snapshot, built at 04:00 UTC, two hours after most nightlies.
